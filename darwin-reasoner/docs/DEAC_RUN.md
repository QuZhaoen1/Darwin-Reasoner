## 1. What is being run

The pilot is three phases over 100 problems, split into 10 disjoint batches of 10, one
Slurm array task per batch.

| Phase | Script | What it does | Rows expected per batch |
|---|---|---|---|
| A1 | `scripts/deac/a1_baselines.sbatch` | E1 baselines: 5 template architectures + self-consistency-8 | 60 = 10 problems x 6 methods |
| A2 | `scripts/deac/a2_collect.sbatch` | E2 matched counterfactual collection | 240 = 10 problems x `execute_top_k` 8 x `repeats_per_architecture` 3 |
| B | `scripts/deac/b_worldmodel.sbatch` | Barrier: merge all batches, train + evaluate the world model, mine macros | — (no LLM calls) |

Run directories are `runs/pilot/batch_XX/{baselines,counterfactual}`; per-batch configs are
`configs/batches/batch_XX.yaml`, generated by `scripts/deac/make_batches.py` from
`configs/pilot_8b.yaml`.

### Why batches rather than one long job

`cli collect` cannot resume. `experiment.py` re-executes every rollout and only then checks
`store.is_completed`, so a requeued or timed-out collect restarts from zero compute and can
never converge. Batching bounds the blast radius: a lost batch costs one batch, and it is
resubmitted alone with `sbatch --array=<k>`. `partition=gpu` has `PreemptMode=REQUEUE`, so
this is not a hypothetical failure mode.

Batches are contiguous (batch *k* is problems `[10k, 10k+10)`), not round-robin, so any gap
in the merged atlas is traceable to exactly one array task.

### Job topology actually submitted

| Job ID | Name | Array | Role |
|---|---|---|---|
| 8300491 | `dr_probe` | — | A/B/C prompting probe (Section 4) |
| 8300510 | `dr_a1` | `0-9%3` | E1 baselines, all 10 batches |
| 8300511 | `dr_a2` | `0` | E2 batch 00, released early |

|---|---|---|---|---|
| `gpu-a100-01,02` | 4 x A100_80 | 64 | 773,610 | yes |

| `gpu-h200-02` | 2 x H200_141 | 64 | 385,000 | drained during this run |
| `gpu-v100-01` | 3 x V100_32 | 64 | 1,031,000 | **excluded** |
| `gpu-v100-02,03,04` | 4 x V100_32 | 64 | 1,031,000 | **excluded** |

Every job therefore carries:

```
#SBATCH --account=yanggrp
#SBATCH --partition=gpu
#SBATCH --gres=gpu:1
#SBATCH --exclude=gpu-v100-01,gpu-v100-02,gpu-v100-03,gpu-v100-04
#SBATCH --mem=96G
```

Three points a reader should not have to rediscover:

- **All four V100 nodes are excluded, not three.** V100 is sm_70 and has no bf16; the run is
  `dtype: bfloat16`. Earlier scripts in this project excluded only `v100-01..03`, landed on
  `v100-04`, and died. `gpu-v100-03/04` additionally advertise a `shard:` GRES, so they can
  be handed out in ways that make the failure look intermittent.
- **`--mem` is mandatory.** The submit plugin rejects a job with
  `slurm_job_submit: Neither --mem nor --mem-per-cpu specified`.
- **Maximum 4 GPUs per node, `MaxNodes=2` for the partition.** There is no 8-GPU node and
  there will not be one. The repository ships `configs/a100_8gpu_32b.yaml`
  (`Qwen3-32B`, `tensor_parallel_size: 8`) and `VALIDATION_8XA100.md`; that configuration
  cannot run on this cluster at all. This pilot uses `Qwen3-8B` at
  `tensor_parallel_size: 1`, which is the first and largest deviation from the repository's
  intended setup.

The partition's `MaxTime` is 28 days, so the 4-hour ceiling used for A2 is *our* choice, not
a limit: short jobs backfill, and combined with `%2`/`%3` array throttling this run coexists
with other users of the account instead of monopolising the queue.

**One GPU per job is not a limitation we are working around; it is the honest allocation.**
`executor.py` issues one prompt per `LLM.generate` call, so vLLM's continuous batching never
engages and the model runs single-stream regardless of how many GPUs are allocated (see
Section 7). Requesting more would have wasted them.

## 4. The prompting defect, and the evidence that established it

### 4.1 The observation

The pre-fix pilot produced a baseline accuracy near 40% on MATH-500 with Qwen3-8B, which is
implausibly low. The question was whether the model was that weak or the harness was losing
correct answers. Job **8300491** answered it: 8 MATH-500 problems, the same problems in all
three conditions, one process, `scripts/deac/probe_prompting.py`.

| Condition | Prompt form | `max_tokens` | Scored by repo verifier | Truncated at cap |
|---|---|---|---|---|
| A | raw completion | 1024 | 1/8 (12%) | **8/8** |
| B | raw completion | 3072 | 2/8 (25%) | **7/8** |
| C | chat template | 3072 | 0/8 (0%) | **0/8** |

Condition C's mean output was ~503 tokens (304, 794, 382, 333, 608, 294, 547, 766).

### 4.2 Two distinct defects, cleanly separated

**Defect 1 — no termination.** Qwen3-8B is instruction-tuned. Fed a bare completion prompt
it emits no EOS: it answers, and then keeps going until `max_tokens`. Condition A's raw
outputs show this directly — the correct answer `(3, π/2)` followed by 36 repetitions of a
zero-width character, `$p - q$` followed by `**.**.**.**...`, the correct
`$\boxed{\frac{14}{3}}$` followed by the model starting its answer over. Raising the cap
from 1024 to 3072 (B) bought one more correct answer and still truncated 7 of 8; it treats
the symptom. Condition C is the fix: with the tokenizer's chat template applied, the model
stops on its own at ~503 tokens and **0/8** truncate.

**Defect 2 — the scorer.** Under C the model got all eight problems right, and the
repository's verifier scored **0/8**:

| # | Model's answer under C | Gold | Correct? | Why the scorer said no |
|---|---|---|---|---|
| 1 | `(3, π/2)**` | `\left( 3, \frac{\pi}{2} \right)` | yes | trailing `**`, `\left/\right`, `\frac`, unicode π |
| 2 | `p - q**` | `p - q` | yes | trailing `**` |
| 3 | `$\boxed{\frac{14}{3}}$**` | `\frac{14}{3}` | yes | trailing `**`, `\boxed`, `\frac` |
| 4 | `9**` | `9` | yes | trailing `**` |
| 5 | `Evelyn**` | `\text{Evelyn}` | yes | trailing `**`, `\text{}` |
| 6 | `42**` | `42` | yes | trailing `**` |
| 7 | `27**` | `27` | yes | trailing `**` |
| 8 | `90**` | `90^\circ` | yes | trailing `**`, `^\circ` |

The model writes `**FINAL: 9**`; the extractor captured `9**` and the normalizer had no rule
for markdown emphasis. Every one of the eight misses is a wrapper, not a mathematical
disagreement.

### 4.3 Why this had to be fixed before the run was worth doing

A verifier bias that is shared across all architectures partly cancels in a within-state
ranking — every candidate is scored by the same broken scorer, and the pilot's gate is a
ranking over candidates that share a state. **Truncation does not cancel.** Architectures
differ in how many calls they issue, and the cap is per call, so a multi-call architecture
gets several times the total token budget of a single-call one. Under condition A, a
single-call CoT gets 1024 tokens to finish in and a debate-then-verify graph gets 1024 per
node. Truncation therefore penalises short single-call architectures *specifically*.

That is a differential bias on exactly the quantity the pre-registered gate measures: it
would have made structural elaboration look better than it is, in the direction the
project's hypothesis predicts. Running the pilot on that apparatus would have produced a
result that could not be defended, whichever way it came out.

## 5. Code changes

Three changes, all in the working tree. **Read them with `cd G:/projects/Darwin-reasoner &&
git diff`**; the summaries below are orientation, not a substitute.

### 5.1 `verifier.py` — `extract_final_answer` crashed on an empty capture

A truncated generation can end with a bare `FINAL:` or an empty `\boxed{}`. The original took
the last regex match unconditionally and called `.strip().splitlines()[0]`, which raises
`IndexError` on an empty capture. This was hit within 8 problems of real data. The fix walks
matches in reverse and skips blank captures instead of indexing into an empty list.

This is a crash fix with no scoring semantics attached.

### 5.2 `verifier.py` — `normalize_answer` and `verify_exact`

The original normalizer stripped `$`, removed **every** comma, collapsed whitespace,
trimmed `.`, and lowercased. It now also strips: markdown emphasis (`**`, `*`, `__`), LaTeX
spacing macros, presentation wrappers (`\left`, `\right`, `\displaystyle`, `\mathrm`,
`\mathbf`), `\text{}`/`\boxed{}`/`\mbox{}`, `\frac{a}{b}` → `a/b`, `\pi` and unicode π → `pi`,
and `^\circ`/`°`. Wrappers are unwrapped in a bounded loop because the brace-free capture
cannot see through a nested `\frac`, so `\boxed{\frac{14}{3}}` only unwraps after the
fraction collapses.

Two choices worth defending explicitly:

- **Only thousands separators are removed now**, not every comma. Removing every comma fused
  the elements of a list answer (`-2, 1` → `-21`), *inventing* mismatches that the original
  code then reported as wrong answers. The narrow rule `(?<=\d),(?=\d{3}(\D|$))` removes
  `1,000` → `1000` and leaves `-2, 1` alone.
- **`verify_exact` gained an order-insensitive comparison, tightly guarded.** It applies only
  when *both* sides are bare top-level lists — a comma with no bracket anywhere in the
  string. `(3, pi/2)`, `{1,2}`, and `[0,1]` are untouched, because there the comma denotes
  position in a tuple or interval and order carries meaning.

Every rule is applied to the prediction and the reference alike, so no comparison is
loosened asymmetrically. The normalizer cannot turn a wrong answer into a right one; it can
only stop rejecting a right one for its packaging.

### 5.3 `config.py` / `vllm_backend.py` / `factory.py` — chat template as an option

Added `backend.use_chat_template` and `backend.enable_thinking`, both defaulting to
**`False`**. When enabled, `VLLMBackend._render` wraps each operator prompt via
`tokenizer.apply_chat_template(..., add_generation_prompt=True,
enable_thinking=self.enable_thinking)` before generation.

The defaults are false on purpose: the original raw-completion behaviour remains the
out-of-the-box behaviour of the repository, and this run's departure from it is visible as
an explicit `use_chat_template: true` in every `configs/batches/batch_XX.yaml` and in each
run directory's `config.resolved.json`. A reader can reproduce the pre-fix behaviour by
regenerating batches with `--raw-prompts`.

**`enable_thinking` is `false` by design for this pilot, and this is a scientific choice, not
an oversight.** The project's premise is that the *architecture* supplies the reasoning
structure. Turning on the model's internal thinking mode would put a second, uncontrolled
source of reasoning structure inside every node of every candidate architecture, and would
confound precisely the comparison the pilot exists to make.

## 6. Configuration and post-fix measurements

### 6.1 Backend configuration for the run

```yaml
backend:
  kind: vllm
  model: Qwen/Qwen3-8B
  tensor_parallel_size: 1
  gpu_memory_utilization: 0.90
  dtype: bfloat16
  max_model_len: 16384
  temperature: 0.6
  top_p: 0.95
  max_tokens_per_call: 2048
  use_chat_template: true      # deviation, Section 5.3
  enable_thinking: false       # deviation, Section 5.3
```

`max_tokens_per_call: 2048` is headroom, not a target. Under the chat template the model
terminates on its own at ~500 tokens; the cap exists so that a genuinely long derivation is
not clipped, not because generations are expected to reach it. Measured cost under this
configuration is ~6.4 s per generation call, against 12.8 s at a 1024-token cap where every
call ran to the cap every time.

Search, budget, counterfactual, world-model and evolution settings are inherited unchanged
from `configs/pilot_8b.yaml` (`num_candidates: 24`, `execute_top_k: 8`,
`repeats_per_architecture: 3`, `max_tokens: 8192`, `max_calls: 16`, hash-MLP ensemble of 5).

## 7. Known limitations this run does **not** address

These were found by an independent review of the repository. They are **not** defects
introduced by the changes above, and none of them is fixed here. They are recorded because
they bound what the pilot's output can be said to mean.

**1. "Matched intermediate reasoning state" is in practice "same problem."**
`experiment.py:182` constructs exactly one `ReasoningState` per problem, with an empty
transcript, and `CounterfactualConfig.max_states_per_problem` is declared in `config.py:48`
and set in the YAMLs (`pilot_8b.yaml` sets 2) but is **read nowhere in `src/`**. The
counterfactual comparison is therefore matched at the problem level, not at a mid-trajectory
state. Claims about intervening on a partially-developed reasoning state are not supported
by this data.

**2. Active design is inert in this run, and the selected 8 are the first 8.**
`pipeline.py:39` calls `collect_counterfactuals(config, run_dir=...)` with no world model,
and `a2_collect.sbatch` likewise passes no `--world-model`. `_make_world_model` then returns
a freshly-initialised `EnsembleWorldModel`, whose predictions carry no information, so
`ActiveCounterfactualDesigner`'s acquisition score is near-constant and the selection
degenerates to a stable-sort passthrough over generation order. Of 24 generated candidates,
the 8 that execute are effectively the first 8 the generator emitted.

For the *first* collection pass this is partly unavoidable — there is no trained world model
before the data that trains it exists. But it means the pilot's E2 is a uniform-ish sample
over generation order, not an actively designed one, and no efficiency claim for active
design can be made from it.

**3. Continuous batching is inert.**
`executor.py:82` calls `self.backend.generate([prompt], ...)` — one prompt per vLLM call.
vLLM's scheduler therefore never has more than one sequence to batch, and the GPU runs
single-stream regardless of allocation. This is the reason a 1-GPU request is the honest
one, and it is the single largest available speedup left on the table.

**4. E5 and E10 have no implementation.** Third-party SOTA baselines (E5) and
experience-time scaling (E10) exist in the protocol documents only. Any comparison against
external methods is currently out of scope for what this codebase can produce.

**5. `enable_thinking: false`** — restated here as a limitation rather than a fix. It is the
right control for this experiment (Section 5.3), but it means the numbers are not
comparable to published Qwen3-8B MATH results obtained with thinking enabled.

**6. Run directories do not record a commit.** The cluster tree is an uploaded copy, not a
git checkout, so `environment.json` records `"git_commit": "unknown"` for every run. A run
directory cannot currently be mapped back to a source revision by machine; this document and
the working-tree diff are the provenance.
